# Lessons Learned

Rules for myself. Read this at session start. Do not repeat these mistakes.

## Session Persistence (CRITICAL)

1. **Always update `tasks/todo.md` and `tasks/lessons.md` before suggesting /clear.** The user lost context between sessions because I did not write handoff notes. This is the #1 process failure.
2. **MEMORY.md is limited to 200 lines.** Put detailed specs in `tasks/` files and link from MEMORY.md.
3. **Git commit messages are searchable context.** Write detailed commit messages that explain WHY, not just what. Future sessions can run `git log` to reconstruct history.

## Code Patterns

4. **Supabase joined tables return arrays.** Always check `Array.isArray()` before casting. This has bitten us multiple times.
5. **Radix UI tabs cannot be clicked via browser automation.** The Chrome extension cannot trigger Radix tab switches via coordinate clicks, ref clicks, or JS dispatched events. Only React fiber props workaround works (unreliable).
6. **React controlled inputs need `form_input` tool**, not the `type` action. Typing doesn't update React state.
7. **`.limit(1).single()` is a common pattern** in our codebase for loading "the one project" or "the one widget." When adding multi-support, grep for ALL occurrences of this pattern.
8. **Widget API `isPro` check must include 'agency'.** Was broken (only checked `=== 'pro'`). Fixed. Pattern: always check `plan === 'free'` (negation) rather than checking for specific paid plans.
9. **Tailwind classes are static at build time.** Cannot use dynamic accent colors in Tailwind gradient classes. Use inline `style` with CSS `linear-gradient()` instead.
10. **embed.js is vanilla JS, not React.** Changes to embed.js are manual DOM string building. Test changes carefully since there's no type checking.

## Product Decisions

11. **"Copy must match reality."** If the pricing page lists a feature, the code must support it. We discovered 6 broken promises during the usability audit. Never add features to marketing copy without implementing them first.
12. **Customer-facing error messages must not leak internal details.** Video limit error was showing "Free plan includes 3 video testimonials. Upgrade to Pro" to the VISITOR who cannot upgrade. Always ask: "Who sees this message? Can they act on it?"
13. **The "KFC test" for brand blending:** On every customer-facing surface, ask "Would this look like KFC built it?" If the answer is no, the brand blending promise is broken.
14. **Optimistic UI reverts need the original state.** Don't blindly revert to 'pending'. Either capture the previous state before the optimistic update, or re-fetch from the DB.
15. **URL params must be supported for all tabs, not just billing.** When adding tab-based navigation, ensure all tabs are URL-addressable (Settings ?tab=project was broken).

## Process

16. **Create git checkpoint before every task.** `git add -A && git commit -m "checkpoint: before [task]"`. This is in CLAUDE.md but I wasn't doing it consistently.
17. **Read tasks/lessons.md at session start.** This file exists specifically to prevent repeated mistakes.
18. **Test with real user flows, not just code review.** The usability testing in browser caught issues that code reading missed (e.g., form title not rendering despite code looking correct at a glance).
19. **Parallel subagents for audits save massive time.** Launching 4 code review agents simultaneously was efficient. Use this pattern for any multi-file audit.
20. **Don't trust subagent claims blindly.** One agent said the image card API route was missing when it actually existed. Always verify critical claims with a direct file check.

## Process Failures (March 4, 2026 session): Prevented by CLAUDE.md Checklists

21. **NEVER skip reading skill files.** I built 21 fixes without reading any of the 5 skill files. The code was fine but the process was wrong. Prevention: CLAUDE.md now has a mandatory pre-implementation checklist that requires listing which skills were read. If the answer is "none," stop.
22. **NEVER skip persona-based testing.** I verified code worked but never tested as "Sarah Chen, freelance designer" or any named persona. A feature can work technically but fail for the human it's built for. Prevention: post-implementation checklist requires naming the persona you tested as.
23. **NEVER skip the security spot check.** New routes and API changes went out without checking auth bypass, RLS, or error message leakage. Prevention: post-implementation checklist requires a security spot check for any new route or API.
24. **NEVER skip validation before building.** I jumped straight to code without confirming each fix passes the "matters" test or "80/50" test. Some fixes might not have been worth the complexity. Prevention: pre-implementation checklist requires explicit validation answers.
25. **NEVER skip end-to-end flow testing.** Changes to the collect form, widget builder, and embed.js were tested in isolation, not as a connected journey. Prevention: post-implementation checklist requires end-to-end flow testing for features touching the customer journey.
26. **NEVER skip interface design skill for UI changes.** Widget builder text color picker and card style selector were built with reasonable defaults but without formal persona intent, subtle layering principles, or token consistency checks. Prevention: pre-implementation checklist requires confirming interface design skill was applied for any UI change.
27. **NEVER suggest /clear without completing the session-end hard gate.** The 5-step shutdown sequence (update todo, update lessons, commit, output handoff, self-check) must ALL be done before suggesting /clear. Past failure: I suggested /clear without writing handoff notes, causing total context loss in the next session. The handoff note self-check question is: "If I lost all memory and only had tasks/todo.md, tasks/lessons.md, and MEMORY.md, could I continue?" If no, the handoff is incomplete.
28. **NEVER write code before completing the session-start hard gate.** The 5-step startup (read todo, read lessons, read skills, understand WHY, create checkpoint) must ALL be done before any code. Past failure: I jumped straight to building 21 fixes without reading any skill files. The startup cost is 2 minutes. The cost of skipping it is process failures that compound across the entire session.
29. **Process improvements are worthless without enforcement.** Session 2 was spent building process gates. The key insight: documented rules are self-policing (can be skipped). Automated hooks + human-visible confirmation phrases are the strongest enforcement available. Always pair a rule with a mechanism that makes skipping it visible.
30. **Test ALL personas, not just the primary one.** Multi-project was tested only as Marcus (agency owner). Testing as a new user with 0 projects revealed a bug: widgets page showed infinite loading spinner because `fetchData` returned early without setting `loadingTestimonials = false`. The "create a project first" banner never appeared. Single-persona testing is not testing. Walk through every persona's journey separately.
31. **Early return guards must clean up loading state.** When a `fetchData` function has `if (!id) return` at the top, any loading flag set to `true` at initialization (e.g., `useState(true)`) will never flip to `false`. Either set loading to `false` before the early return, or initialize loading as `false` and only set it `true` after the guard passes.
32. **Happy path testing is not testing.** Multi-project was built and "tested" by only tracing the happy path for one persona. Missed: new user (0 projects, infinite loading bug), free user at limit (gate behavior), downgraded user (5 projects on free plan). The fix: enumerate ALL test scenario categories BEFORE writing code (personas, empty state, boundaries, plan transitions, stale data, concurrent state, failures, permissions, reverse actions). This list becomes the verification checklist after implementation. If you didn't list it, you won't test it.
33. **Extract helpers before adding complexity.** When adding multi-widget to a 1272-line file, extracting `loadWidgetIntoSettings` and `DEFAULT_SETTINGS` first made the diff much cleaner than trying to inline everything. Pattern: extract shared logic into named functions/constants before adding the new feature.
34. **Plan gate checks should use `totalWidgetCount` across all projects, not per-project count.** Free plan limit is "1 widget total" not "1 widget per project." The counter must query all widgets for user_id, not just the current project. Same principle applies to forms.
35. **NEVER pick UI patterns before writing persona intents.** Multi-widget used a horizontal pill bar because "the layout selector already uses pills." That is defaulting, not designing. The correct process: (1) write a Persona UI Intent for EACH affected persona (name, device, context, task, feel), (2) evaluate whether the proposed component serves each persona, (3) if it fails for any persona, find a better solution or present the tradeoff. A pill bar might be perfect for a desktop agency owner but wrong for a mobile freelancer. Writing the intents first makes this obvious. Skipping them makes it invisible.
36. **Every UI decision must pass the "everyone happy" test.** Three questions: (1) Does this work for every persona on their actual device? (2) Does this reduce friction or increase it? (3) Does this support the business (retention, upgrades, referrals)? If ANY persona is left out, the design is incomplete. This applies to plans too: plans that propose UI must include persona intents, not just "add a selector bar."
37. **Business impact is not an afterthought.** The widget selector upgrade dialog copy and placement were copied from the forms page without asking: "Is the free plan limit (1 widget) generous enough for the user to experience multi-widget value before hitting the gate?" If they never experience switching between widgets, the upgrade prompt has no motivation behind it. Business impact must be evaluated alongside persona intents, not bolted on as "Business: looks fine" at the end. The six questions: retention, conversion, time to value, churn risk, expansion, referral.
38. **Shadow DOM font loading requires link tags inside the shadow root.** External CSS (like Google Fonts) must be injected as `<link>` elements directly into the shadow root, not the host page `<head>`. Fonts loaded in the host page may not be accessible inside shadow DOM in all browsers. Preconnect hints also go inside the shadow root.
39. **updateTheme helper types must match the widest field type.** When adding nullable fields to WidgetTheme (like `fontUrl: string | null`), the `updateTheme` callback signature must accept `null` too, not just `string | boolean`. TypeScript catches this at build time.
40. **Font sanitization must cover both URL and family name.** URLs: HTTPS-only, reject javascript:/data: URIs. Family names: strip everything except `[a-zA-Z0-9 -]` to prevent CSS injection via `; color: red` or similar.
41. **`font-display: optional` causes first-load font fallback that never swaps.** The browser uses the fallback font (Arial) and does NOT swap to the custom font for that page load. Only on subsequent cached loads does the font appear. Use `display: 'swap'` for web fonts where you always want the custom font to load.
42. **Centralize feature lists and plan definitions.** Having PRO_FEATURES defined in 3 separate files (modal, settings, pricing cards) led to divergent lists. One file had 8 features, another 10, another 11. Export from a single source (`src/lib/lemonsqueezy.ts`) and import everywhere.
43. **Never hardcode prices in button labels.** "Upgrade to Pro, $19/mo" scattered across 4 files means 4 places to update when pricing changes. Use the shared UpgradeModal instead of inline upgrade dialogs with hardcoded prices.
44. **Supabase query builder types don't work with generic helper functions.** Passing a Supabase query through a helper function like `applyScope(query)` causes "Type instantiation is excessively deep and possibly infinite." Use a `scopeKey`/`scopeVal` pattern instead: `const scopeKey = useProject ? 'project_id' : 'user_id'; query.eq(scopeKey, scopeVal)`.
45. **Modal content must fit the viewport without scrolling.** A scrollbar on a modal ruins the UI. If content is too tall, condense it (combine related items, use shorter copy) rather than adding overflow scroll. The pricing page can show the full list; the modal shows highlights.
46. **Contradictory pricing copy erodes trust.** Showing "$49/month" and "Custom pricing for larger teams" on the same card is confusing. Pick one message. If the price is fixed, say so. If it's custom, don't show a number.
47. **Blob URL video needs `preload="auto"` for instant playback.** Without it, browsers may not buffer the blob until the user clicks play, causing a 5-8 second delay. Blob URLs are local (no network), so `preload="auto"` is safe and instant.
48. **Lower getUserMedia resolution for faster camera init.** `ideal: 1280x720` forces hardware negotiation at HD. `ideal: 640x480` is faster and sufficient when recording at 600kbps. The `ideal` constraint means higher-res cameras still work (they just scale down).
49. **Thumbnail-first is the default for embedded video.** Never autoload video in widgets. Use poster image + play button, create `<video>` on click. This is how YouTube/Vimeo embeds work. Saves 70-90% bandwidth since most visitors never click play on every testimonial.
50. **embed.js `replaceWith()` is one-way.** Once the poster div is replaced with a `<video>` element, the poster is gone. If the parent re-renders (e.g., carousel navigation), the video state is lost. Acceptable for current layouts but worth noting for future interactive layouts.
51. **Radix DialogContent requires DialogTitle.** Without it, a console error fires about accessibility. If the dialog has a custom header (not using DialogTitle), add a `<DialogTitle className="sr-only">` for screen readers.
52. **Never list features that don't exist.** "Priority email support" and "Custom onboarding call" were in AGENCY_FEATURES but had no product implementation. Feature lists must match shipped product. Audit feature lists whenever shipping new capabilities.
53. **Subagent claims need verification for critical findings.** During the audit, the product-strategist agent claimed `/api/testimonials/card/[id]` route didn't exist. The test-suite-architect agent confirmed it DOES exist and builds successfully. Lesson #20 reinforced: always verify critical claims with a direct file check before acting on them.
54. **Webhook plan mapping must cover ALL paid plans.** The webhook sets `plan: 'pro'` for all active subscriptions. Agency subscribers get silently downgraded to Pro features on renewal. Pattern: when adding a new paid plan, always update the webhook handler to map variant IDs to the correct plan string.
55. **Security headers are not optional for launch.** next.config.ts had zero security headers (no CSP, X-Frame-Options, HSTS, nosniff). This is a basic security requirement, not polish. Add headers config during initial project setup, not as an afterthought.
56. **Auth callback open redirect: always validate redirect targets.** The `next` query parameter in auth callback was passed directly to `redirect()` without validation. Attacker can set `next=//evil.com` to redirect users after login. Fix: validate that `next` starts with `/` and does not start with `//`.
57. **File upload routes need extension allowlisting, not just MIME checking.** Logo upload accepted any file type because it only checked Content-Type header (client-controlled). An attacker can upload an HTML file with `image/png` MIME type. Fix: validate file extension AND MIME type AND use content sniffing.
58. **Run a full product audit before launch, not just feature reviews.** 12 agents found 35+ issues across security, UX, performance, copy, and competitive positioning that individual feature sessions missed. Pattern: schedule a dedicated audit session before any major launch milestone.
59. **CSP must exempt embed routes.** X-Frame-Options: SAMEORIGIN and frame-ancestors 'self' in CSP block iframe embedding on customer sites. Embed routes and widget API routes must be excluded from these headers. Use Next.js `headers()` with negative lookahead regex or separate source entries.
60. **Admin secret guard: `!secret` not `secret &&`.** The pattern `if (adminSecret && header !== adminSecret)` passes when adminSecret is undefined (the whole condition is false, so the guard is skipped). Correct pattern: `if (!adminSecret || header !== adminSecret)`. This is a classic "fail open" vs "fail closed" mistake.
61. **Verify deps are actually unused before npm uninstall.** The audit said 6 unused deps but `next-themes` is used by sonner (toast library). Always grep for imports before removing. `cmdk` was imported by `command.tsx` but nothing imported `command.tsx`, making it transitively unused.
62. **Archived .tsx files still get type-checked.** Moving a file to `_archive/` doesn't exclude it from TypeScript if tsconfig includes `**/*.tsx`. Add `_archive` to tsconfig `exclude` array.
63. **dangerouslySetInnerHTML works for inline SVGs in React.** For trust bars and icon sets where SVG paths come from a data array, `<svg dangerouslySetInnerHTML={{ __html: path }}>` is the cleanest pattern. The data is developer-controlled (not user input), so no XSS risk.
64. **When parallelizing DB queries with Promise.all, pre-query limits must be generous.** Moving a query before a plan check means you don't know the user's `max_items` yet. Use a generous upper bound (e.g., `Math.max(widget.max_items, 50)`) instead of a hardcoded small number. The post-query `.slice()` handles the real limit.
65. **Error checks must come before data processing.** If `testimonialError` is checked after sorting/slicing `rawTestimonials`, the error check is dead code (rawTestimonials is null on error, so `[]` is used and processing completes before reaching the check).
66. **API JSON endpoints still need `nosniff` header.** Even if you exclude API routes from full CSP/X-Frame-Options headers, they should still get `X-Content-Type-Options: nosniff` to prevent MIME-sniffing of JSON as HTML.
67. **SVG uploads are a stored XSS vector.** SVG files can contain `<script>` tags and event handlers. Allowing SVG upload without server-side sanitization (e.g., DOMPurify) means an attacker can upload malicious SVGs. Consider removing SVG from upload allowlists or sanitizing before storage.
68. **ALWAYS run a senior dev review agent before committing.** Session 11 caught a HIGH bug (widget API fetchLimit regression) and 5 medium issues that would have shipped unreviewed. The review agent (general-purpose) should review every diff before it's committed. This is now baked into the post-implementation gate.
69. **Use agents proactively, not just when asked.** Explore agent for codebase searches (saves main context), Plan agent before non-trivial features, db-optimizer for schema changes, general-purpose for reviews. Parallelize independent agents in one message. Don't duplicate agent work by also searching inline.
