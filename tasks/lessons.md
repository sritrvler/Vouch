# Lessons Learned

Rules for myself. Read this at session start. Do not repeat these mistakes.

## Production Schema Sync (Session 20)
Production Supabase schema was missing columns added via ALTER TABLE in later sessions. The code queries all columns, so missing columns cause 400 errors. Before seeding or testing on prod, always verify the schema is fully up to date. The full list of ALTER TABLE statements is in `supabase/schema.sql` as comments.

## SQL Copying from Chat (Session 20)
Copying multi-line SQL from chat into Supabase SQL Editor introduces hidden carriage return characters (0x0d) that break JSON parsing. Fix: write SQL to a file and have user copy from the file instead.

## Session Persistence (CRITICAL)

1. **Always update `tasks/todo.md` and `tasks/lessons.md` before suggesting /clear.** The user lost context between sessions because I did not write handoff notes. This is the #1 process failure.
2. **MEMORY.md is limited to 200 lines.** Put detailed specs in `tasks/` files and link from MEMORY.md.
3. **Git commit messages are searchable context.** Write detailed commit messages that explain WHY, not just what. Future sessions can run `git log` to reconstruct history.

## Code Patterns

4. **Supabase joined tables return arrays.** Always check `Array.isArray()` before casting. This has bitten us multiple times.
5. **Radix UI tabs cannot be clicked via browser automation.** The Chrome extension cannot trigger Radix tab switches via coordinate clicks, ref clicks, or JS dispatched events. Only React fiber props workaround works (unreliable).
6. **React controlled inputs need `form_input` tool**, not the `type` action. Typing doesn't update React state.
7. **`.limit(1).single()` is a common pattern** in our codebase for loading "the one project" or "the one widget." When adding multi-support, grep for ALL occurrences of this pattern.
8. **Widget API `isPro` check must include 'agency'.** Was broken (only checked `=== 'pro'`). Fixed. Pattern: always check `plan === 'free'` (negation) rather than checking for specific paid plans.
9. **Tailwind classes are static at build time.** Cannot use dynamic accent colors in Tailwind gradient classes. Use inline `style` with CSS `linear-gradient()` instead.
10. **embed.js is vanilla JS, not React.** Changes to embed.js are manual DOM string building. Test changes carefully since there's no type checking.

## Vercel Environment Variables (Session 22)
13. **Vercel team-level vs project-level env vars:** Project-level takes precedence over team-level. If an env var exists at both levels, the project-level value is used. Always add env vars at the project level for the specific project. Team-level is only for vars shared across ALL projects.
14. **Env var changes require redeployment.** Saving env vars in Vercel does not apply them to the running deployment. You must redeploy (new deployment, not just "Redeploy" button on old one) for changes to take effect.
15. **Debug undefined env vars in JSON:** `JSON.stringify` strips `undefined` values. If a field is missing from a JSON API response, the env var is not set. This is a reliable way to confirm env var availability without needing server logs.
16. **Lemon Squeezy test vs live mode:** API keys, variant IDs, and store IDs are separate between test and live mode. Store ID happens to be the same, but API keys and variants are different. Always keep test keys in `.env.local` and live keys in Vercel project settings.

## Product Decisions

11. **"Copy must match reality."** If the pricing page lists a feature, the code must support it. We discovered 6 broken promises during the usability audit. Never add features to marketing copy without implementing them first.
12. **Customer-facing error messages must not leak internal details.** Video limit error was showing "Free plan includes 3 video testimonials. Upgrade to Pro" to the VISITOR who cannot upgrade. Always ask: "Who sees this message? Can they act on it?"
13. **The "KFC test" for brand blending:** On every customer-facing surface, ask "Would this look like KFC built it?" If the answer is no, the brand blending promise is broken.
14. **Optimistic UI reverts need the original state.** Don't blindly revert to 'pending'. Either capture the previous state before the optimistic update, or re-fetch from the DB.
15. **URL params must be supported for all tabs, not just billing.** When adding tab-based navigation, ensure all tabs are URL-addressable (Settings ?tab=project was broken).

## Process Failures (March 4, 2026 session): Prevented by CLAUDE.md Checklists

21. **NEVER skip reading skill files.** I built 21 fixes without reading any of the 5 skill files. The code was fine but the process was wrong. Prevention: CLAUDE.md now has a mandatory pre-implementation checklist that requires listing which skills were read. If the answer is "none," stop.
22. **NEVER skip persona-based testing.** I verified code worked but never tested as "Sarah Chen, freelance designer" or any named persona. A feature can work technically but fail for the human it's built for. Prevention: post-implementation checklist requires naming the persona you tested as.
23. **NEVER skip the security spot check.** New routes and API changes went out without checking auth bypass, RLS, or error message leakage. Prevention: post-implementation checklist requires a security spot check for any new route or API.
24. **NEVER skip validation before building.** I jumped straight to code without confirming each fix passes the "matters" test or "80/50" test. Some fixes might not have been worth the complexity. Prevention: pre-implementation checklist requires explicit validation answers.
25. **NEVER skip end-to-end flow testing.** Changes to the collect form, widget builder, and embed.js were tested in isolation, not as a connected journey. Prevention: post-implementation checklist requires end-to-end flow testing for features touching the customer journey.
26. **NEVER skip interface design skill for UI changes.** Widget builder text color picker and card style selector were built with reasonable defaults but without formal persona intent, subtle layering principles, or token consistency checks. Prevention: pre-implementation checklist requires confirming interface design skill was applied for any UI change.
27. **NEVER suggest /clear without completing the session-end hard gate.** The 5-step shutdown sequence (update todo, update lessons, commit, output handoff, self-check) must ALL be done before suggesting /clear. Past failure: I suggested /clear without writing handoff notes, causing total context loss in the next session. The handoff note self-check question is: "If I lost all memory and only had tasks/todo.md, tasks/lessons.md, and MEMORY.md, could I continue?" If no, the handoff is incomplete.
28. **NEVER write code before completing the session-start hard gate.** The 5-step startup (read todo, read lessons, read skills, understand WHY, create checkpoint) must ALL be done before any code. Past failure: I jumped straight to building 21 fixes without reading any skill files. The startup cost is 2 minutes. The cost of skipping it is process failures that compound across the entire session.
29. **Process improvements are worthless without enforcement.** Session 2 was spent building process gates. The key insight: documented rules are self-policing (can be skipped). Automated hooks + human-visible confirmation phrases are the strongest enforcement available. Always pair a rule with a mechanism that makes skipping it visible.
30. **Test ALL personas, not just the primary one.** Multi-project was tested only as Marcus (agency owner). Testing as a new user with 0 projects revealed a bug: widgets page showed infinite loading spinner because `fetchData` returned early without setting `loadingTestimonials = false`. The "create a project first" banner never appeared. Single-persona testing is not testing. Walk through every persona's journey separately.
31. **Early return guards must clean up loading state.** When a `fetchData` function has `if (!id) return` at the top, any loading flag set to `true` at initialization (e.g., `useState(true)`) will never flip to `false`. Either set loading to `false` before the early return, or initialize loading as `false` and only set it `true` after the guard passes.
32. **Happy path testing is not testing.** Multi-project was built and "tested" by only tracing the happy path for one persona. Missed: new user (0 projects, infinite loading bug), free user at limit (gate behavior), downgraded user (5 projects on free plan). The fix: enumerate ALL test scenario categories BEFORE writing code (personas, empty state, boundaries, plan transitions, stale data, concurrent state, failures, permissions, reverse actions). This list becomes the verification checklist after implementation. If you didn't list it, you won't test it.
33. **Extract helpers before adding complexity.** When adding multi-widget to a 1272-line file, extracting `loadWidgetIntoSettings` and `DEFAULT_SETTINGS` first made the diff much cleaner than trying to inline everything. Pattern: extract shared logic into named functions/constants before adding the new feature.
34. **Plan gate checks should use `totalWidgetCount` across all projects, not per-project count.** Free plan limit is "1 widget total" not "1 widget per project." The counter must query all widgets for user_id, not just the current project. Same principle applies to forms.
35. **NEVER pick UI patterns before writing persona intents.** Multi-widget used a horizontal pill bar because "the layout selector already uses pills." That is defaulting, not designing. The correct process: (1) write a Persona UI Intent for EACH affected persona (name, device, context, task, feel), (2) evaluate whether the proposed component serves each persona, (3) if it fails for any persona, find a better solution or present the tradeoff. A pill bar might be perfect for a desktop agency owner but wrong for a mobile freelancer. Writing the intents first makes this obvious. Skipping them makes it invisible.
36. **Every UI decision must pass the "everyone happy" test.** Three questions: (1) Does this work for every persona on their actual device? (2) Does this reduce friction or increase it? (3) Does this support the business (retention, upgrades, referrals)? If ANY persona is left out, the design is incomplete. This applies to plans too: plans that propose UI must include persona intents, not just "add a selector bar."
37. **Business impact is not an afterthought.** The widget selector upgrade dialog copy and placement were copied from the forms page without asking: "Is the free plan limit (1 widget) generous enough for the user to experience multi-widget value before hitting the gate?" If they never experience switching between widgets, the upgrade prompt has no motivation behind it. Business impact must be evaluated alongside persona intents, not bolted on as "Business: looks fine" at the end. The six questions: retention, conversion, time to value, churn risk, expansion, referral.
38. **Shadow DOM font loading requires link tags inside the shadow root.** External CSS (like Google Fonts) must be injected as `<link>` elements directly into the shadow root, not the host page `<head>`. Fonts loaded in the host page may not be accessible inside shadow DOM in all browsers. Preconnect hints also go inside the shadow root.
39. **updateTheme helper types must match the widest field type.** When adding nullable fields to WidgetTheme (like `fontUrl: string | null`), the `updateTheme` callback signature must accept `null` too, not just `string | boolean`. TypeScript catches this at build time.
40. **NEVER skip the Code Quality Pipeline.** User has explicitly and repeatedly requested: (1) architect reviews plan before code, (2) senior dev reviews code after writing, (3) QA generates test cases, (4) tests are run and bugs fixed, (5) senior dev re-reviews final diff, (6) QA verifies fixes, (7) only then commit/push. This 7-step pipeline is documented in CLAUDE.md and MEMORY.md. Skipping any step is a process violation. The user checks for confirmation phrases at each step. This is the #1 user frustration point: agents not being used despite being documented. NEVER shortcut this process.
41. **Use service role client ONLY when RLS must be bypassed.** In the portal URL caching fix, the initial implementation used a service role admin client to write back to the subscriptions table. Senior dev review correctly flagged this: the authenticated user client already has RLS permission to update their own row. Service role bypasses RLS entirely and creates pattern risk if copy-pasted. Only use service role for webhooks, admin operations, and cases where the acting user genuinely cannot write the row.
42. **Validate external URLs before serving them from cache.** When caching URLs from third-party services (like Lemon Squeezy portal URLs) in the database, validate the domain before returning them to the client. RLS allows users to write to their own rows, so a malicious user could set the cached URL to a phishing link. Validate with `new URL(url).hostname.endsWith('.lemonsqueezy.com')` or equivalent.
40. **Font sanitization must cover both URL and family name.** URLs: HTTPS-only, reject javascript:/data: URIs. Family names: strip everything except `[a-zA-Z0-9 -]` to prevent CSS injection via `; color: red` or similar.
41. **`font-display: optional` causes first-load font fallback that never swaps.** The browser uses the fallback font (Arial) and does NOT swap to the custom font for that page load. Only on subsequent cached loads does the font appear. Use `display: 'swap'` for web fonts where you always want the custom font to load.
42. **Centralize feature lists and plan definitions.** Having PRO_FEATURES defined in 3 separate files (modal, settings, pricing cards) led to divergent lists. One file had 8 features, another 10, another 11. Export from a single source (`src/lib/lemonsqueezy.ts`) and import everywhere.
43. **Never hardcode prices in button labels.** "Upgrade to Pro, $19/mo" scattered across 4 files means 4 places to update when pricing changes. Use the shared UpgradeModal instead of inline upgrade dialogs with hardcoded prices.
44. **Supabase query builder types don't work with generic helper functions.** Passing a Supabase query through a helper function like `applyScope(query)` causes "Type instantiation is excessively deep and possibly infinite." Use a `scopeKey`/`scopeVal` pattern instead: `const scopeKey = useProject ? 'project_id' : 'user_id'; query.eq(scopeKey, scopeVal)`.
45. **Modal content must fit the viewport without scrolling.** A scrollbar on a modal ruins the UI. If content is too tall, condense it (combine related items, use shorter copy) rather than adding overflow scroll. The pricing page can show the full list; the modal shows highlights.
46. **Contradictory pricing copy erodes trust.** Showing "$49/month" and "Custom pricing for larger teams" on the same card is confusing. Pick one message. If the price is fixed, say so. If it's custom, don't show a number.
47. **Blob URL video needs `preload="auto"` for instant playback.** Without it, browsers may not buffer the blob until the user clicks play, causing a 5-8 second delay. Blob URLs are local (no network), so `preload="auto"` is safe and instant.
48. **Lower getUserMedia resolution for faster camera init.** `ideal: 1280x720` forces hardware negotiation at HD. `ideal: 640x480` is faster and sufficient when recording at 600kbps. The `ideal` constraint means higher-res cameras still work (they just scale down).
49. **Thumbnail-first is the default for embedded video.** Never autoload video in widgets. Use poster image + play button, create `<video>` on click. This is how YouTube/Vimeo embeds work. Saves 70-90% bandwidth since most visitors never click play on every testimonial.
50. **embed.js `replaceWith()` is one-way.** Once the poster div is replaced with a `<video>` element, the poster is gone. If the parent re-renders (e.g., carousel navigation), the video state is lost. Acceptable for current layouts but worth noting for future interactive layouts.
51. **Radix DialogContent requires DialogTitle.** Without it, a console error fires about accessibility. If the dialog has a custom header (not using DialogTitle), add a `<DialogTitle className="sr-only">` for screen readers.
52. **Never list features that don't exist.** "Priority email support" and "Custom onboarding call" were in AGENCY_FEATURES but had no product implementation. Feature lists must match shipped product. Audit feature lists whenever shipping new capabilities.
53. **Subagent claims need verification for critical findings.** During the audit, the product-strategist agent claimed `/api/testimonials/card/[id]` route didn't exist. The test-suite-architect agent confirmed it DOES exist and builds successfully. Lesson #20 reinforced: always verify critical claims with a direct file check before acting on them.
54. **Webhook plan mapping must cover ALL paid plans.** The webhook sets `plan: 'pro'` for all active subscriptions. Agency subscribers get silently downgraded to Pro features on renewal. Pattern: when adding a new paid plan, always update the webhook handler to map variant IDs to the correct plan string.
55. **Security headers are not optional for launch.** next.config.ts had zero security headers (no CSP, X-Frame-Options, HSTS, nosniff). This is a basic security requirement, not polish. Add headers config during initial project setup, not as an afterthought.
56. **Auth callback open redirect: always validate redirect targets.** The `next` query parameter in auth callback was passed directly to `redirect()` without validation. Attacker can set `next=//evil.com` to redirect users after login. Fix: validate that `next` starts with `/` and does not start with `//`.
57. **File upload routes need extension allowlisting, not just MIME checking.** Logo upload accepted any file type because it only checked Content-Type header (client-controlled). An attacker can upload an HTML file with `image/png` MIME type. Fix: validate file extension AND MIME type AND use content sniffing.
58. **Run a full product audit before launch, not just feature reviews.** 12 agents found 35+ issues across security, UX, performance, copy, and competitive positioning that individual feature sessions missed. Pattern: schedule a dedicated audit session before any major launch milestone.
59. **CSP must exempt embed routes.** X-Frame-Options: SAMEORIGIN and frame-ancestors 'self' in CSP block iframe embedding on customer sites. Embed routes and widget API routes must be excluded from these headers. Use Next.js `headers()` with negative lookahead regex or separate source entries.
60. **Admin secret guard: `!secret` not `secret &&`.** The pattern `if (adminSecret && header !== adminSecret)` passes when adminSecret is undefined (the whole condition is false, so the guard is skipped). Correct pattern: `if (!adminSecret || header !== adminSecret)`. This is a classic "fail open" vs "fail closed" mistake.
61. **Verify deps are actually unused before npm uninstall.** The audit said 6 unused deps but `next-themes` is used by sonner (toast library). Always grep for imports before removing. `cmdk` was imported by `command.tsx` but nothing imported `command.tsx`, making it transitively unused.
62. **Archived .tsx files still get type-checked.** Moving a file to `_archive/` doesn't exclude it from TypeScript if tsconfig includes `**/*.tsx`. Add `_archive` to tsconfig `exclude` array.
63. **dangerouslySetInnerHTML works for inline SVGs in React.** For trust bars and icon sets where SVG paths come from a data array, `<svg dangerouslySetInnerHTML={{ __html: path }}>` is the cleanest pattern. The data is developer-controlled (not user input), so no XSS risk.
64. **When parallelizing DB queries with Promise.all, pre-query limits must be generous.** Moving a query before a plan check means you don't know the user's `max_items` yet. Use a generous upper bound (e.g., `Math.max(widget.max_items, 50)`) instead of a hardcoded small number. The post-query `.slice()` handles the real limit.
65. **Error checks must come before data processing.** If `testimonialError` is checked after sorting/slicing `rawTestimonials`, the error check is dead code (rawTestimonials is null on error, so `[]` is used and processing completes before reaching the check).
66. **API JSON endpoints still need `nosniff` header.** Even if you exclude API routes from full CSP/X-Frame-Options headers, they should still get `X-Content-Type-Options: nosniff` to prevent MIME-sniffing of JSON as HTML.
67. **SVG uploads are a stored XSS vector.** SVG files can contain `<script>` tags and event handlers. Allowing SVG upload without server-side sanitization (e.g., DOMPurify) means an attacker can upload malicious SVGs. Consider removing SVG from upload allowlists or sanitizing before storage.
68. **ALWAYS run a senior dev review agent before committing.** Session 11 caught a HIGH bug (widget API fetchLimit regression) and 5 medium issues that would have shipped unreviewed. The review agent (general-purpose) should review every diff before it's committed. This is now baked into the post-implementation gate.
69. **Use agents proactively, not just when asked.**
70. **When renaming a plan/concept across the codebase, use Explore agent first to find ALL occurrences.** The Agency-to-Studio rename touched 19 files, 112 occurrences. Missing even one would leave an inconsistency. Pattern: `grep -rn 'agency\|Agency\|AGENCY' src/ --include='*.ts' --include='*.tsx'` before AND after the rename.
71. **Test pure business logic functions, not just security validators.** The first test suite only covered security (sanitizers, guards). The second round added plan definitions, webhook mapping, disposable email detection, and font resolution. These are the functions most likely to regress during feature changes. Explore agent for codebase searches (saves main context), Plan agent before non-trivial features, db-optimizer for schema changes, general-purpose for reviews. Parallelize independent agents in one message. Don't duplicate agent work by also searching inline.
72. **Agent usage must be enforced by gates, not by memory alone.** Session 14: agent strategy existed in MEMORY.md since session 8, but was ignored for 3 consecutive tasks (16 a11y fixes across 7 files with zero agents used). Having a strategy documented is not the same as following it. Fix: agent routing is now step 2 of the pre-implementation gate (mandatory, must list agents and justify). Post-implementation gate step 6 now requires verifying each listed agent actually ran. The pattern: if a rule keeps getting skipped, move it into a hard gate with a visible confirmation phrase. Documentation without enforcement is decoration.
73. **"No ARIA is better than bad ARIA."** Using role="tab" without implementing the full keyboard spec (arrow keys, tabindex management, aria-controls) creates a worse screen reader experience than no roles at all. The review agent caught this. For binary toggles, use role="radiogroup"/role="radio" instead of tablist/tab. Simpler keyboard requirements, correct semantics.
74. **aria-label on generic elements (span, div) is ignored by most screen readers.** Use visually hidden text (`<span className="sr-only">`) inside the element instead. aria-label only works reliably on interactive elements or elements with explicit ARIA roles.
75. **Mobile safe area must be accounted for in sticky positioning.** `bottom-20` (5rem) clears a standard mobile nav, but on iPhone with home indicator, safe-area-inset-bottom adds extra space. Use `calc(5rem + env(safe-area-inset-bottom))` to handle both.
76. **Agent delegation requires a written plan with non-overlapping scopes.** Session 13: launched 3 review agents (UX Copy, UI Animation, Accessibility) that all flagged the same ARIA issues. Wasted tokens on duplicate findings, then had to deduplicate manually. Fix: before launching multiple agents, write a Delegation Plan defining exact scope and exclusions per agent. Split by concern, not by file. If Agent A covers accessibility, Agent B must explicitly exclude it. Consolidate all findings into one action list before writing code.
77. **Every agent needs a north star.** Without one, agents produce generic output that doesn't serve the product's specific goals. A north star is one sentence defining what "best output" looks like. It's not a description of what the agent does, it's a measure of whether it succeeded.
78. **Agents that overlap WILL produce duplicate work.** product-strategist had a "Competitive Analysis Framework" that duplicated competitive-analyst. competitive-analyst had "Next 3 Things to Build" that duplicated product-strategist. Fix: define explicit scope boundaries in each agent file ("You DO / You DO NOT") and remove any functionality that belongs to another agent.
79. **competitive-analyst must use live data, not knowledge cutoff.** Competitor pricing, features, and positioning change constantly. WebSearch and WebFetch are mandatory before any competitive claim. Date-stamp every data point. If live check fails, state "last known data from [date], may be outdated."
80. **Confirmation phrases without checklists are weak guardrails.** Step 1 had one phrase covering 4 sub-steps (strategic agents, flow design, feasibility check, architect). Could say the phrase while skipping 3 of 4. Fix: completion checklists with named lines. Every line must have a value. The user sees the checklist and can immediately spot blanks. Applied to Step 1 (7 lines) and Step 3 (9 lines).
81. **UI flow must be designed BEFORE code, not reviewed AFTER.** Industry standard: UX defines the journey (screens, states, sequence) before a single component is built. Changing a wireframe takes 5 minutes, changing built code takes hours. ux-reviewer now has FLOW DESIGN mode (Step 1) and IMPLEMENTATION REVIEW mode (Step 3). Different tasks, no redundancy.
82. **Subagents re-read entire files from scratch.** Each agent starts with zero context. Asking 2 agents to "read and review these 6 files" means each re-reads all 6, doubling token cost. Fix: paste code snippets/diffs directly into agent prompts. Include 10-20 lines of surrounding context per changed section. Never say "read the file at path X."
83. **One-size-fits-all pipelines waste tokens on small tasks.** Launching 3 review agents + 1 test agent for 4 CSS bug fixes consumed ~200K tokens with no quality gain over an inline self-review. Fix: tiered pipeline. T1 (trivial) = no pipeline. T2 (small) = inline self-review only. T3 (medium) = 1-2 agents + self-review. T4 (large) = full agents + self-review. Classify BEFORE starting. Classify UP when in doubt, never down.
84. **Self-review bias is real and predictable.** You will skip over your own bugs because you remember your intent, not what you wrote. Countermeasures: (1) read the diff line-by-line as if someone else wrote it, (2) assume at least 1 bug exists, (3) use a mechanical 9-point checklist, (4) if you find zero issues, do a second pass and justify why zero is credible. "Looks good to me" is never acceptable as a review output.
85. **Shared Radix Popover state between CSS-hidden elements causes dual portal renders.** Two Popovers controlled by the same `open` state but toggled by `hidden md:flex` / `md:hidden` are both mounted in the DOM simultaneously. Opening one opens both (one off-screen). Fix: use separate state variables for desktop and mobile popovers.
86. **Native `<input type="color">` is useless on mobile.** Android Chrome/Firefox show a limited swatch picker with no hex input. Replace with preset buttons + hex text input + color preview swatch. No external library needed.
87. **"Request desktop site" on mobile reports viewport ~980px.** This triggers `md:` (768px) breakpoints but not `lg:` (1024px). Three-column grids at `md:grid-cols-3` overlap badly at 980px fake viewport on a 412px physical screen. Fix: use `lg:grid-cols-3` (1024px) for marketing grids. Add `sm:grid-cols-2` for real tablet intermediate step.
88. **Radix Popover hydration mismatch: defer rendering with `mounted` state.** Radix generates different random IDs during SSR vs client, causing aria-controls mismatch errors. Fix: `const [mounted, setMounted] = useState(false); useEffect(() => setMounted(true), []);` then render static placeholder buttons when `!mounted`, Popovers only when `mounted`. Apply to ALL Popovers/Tooltips that render on initial page load.
89. **Always include user_id in Supabase queries, not just project_id.** Filtering by `project_id` alone trusts that the project belongs to the user. RLS should catch this, but defense-in-depth means always adding `.eq('user_id', user.id)` alongside project scoping. Senior review caught this gap in inbox and overview pages.
90. **Radix Select `position="popper"` for correct dropdown direction.** Default `position="item-aligned"` makes the dropdown appear to go upward by aligning the selected item with the trigger. Use `position="popper"` with `sideOffset={4}` for standard dropdown-below behavior.
91. **Dialog input contrast: never use `bg-transparent` on white dialogs.** Inputs with transparent background on a white dialog look indistinguishable from the background. Always use `bg-white border-border` for editable inputs and `bg-muted cursor-not-allowed` for locked/disabled fields.
92. **Project selectors in dialogs should respect global context.** When a specific project is selected in the sidebar, dialogs should pre-select and lock that project. When "All projects" is active, dialogs should show an editable dropdown. This prevents confusion about which project receives the new item.
93. **"Continuing previous work" is NOT an excuse to skip the pipeline.** Session 15: agent reviews ran in the previous session, then context was compacted. New session applied 10 fixes from old agent output without classifying tier, without running a fresh pipeline, without any confirmation phrases. The rationalization was "these are just patches from already-reviewed findings." But 10 coordinated changes to a 1700-line component (animation refactor, sticky positioning, state changes, new imports) is T3, not "finishing up." **Rule: if you write new code, you run a new pipeline. Period.** Old agent output is input to your plan, not a substitute for the pipeline. The trigger is "did I write code?" not "was this code already discussed?"
94. **UI-heavy T3+ tasks MUST run BOTH `premium-ui-designer` AND `ux-reviewer`.** Session 14 (previous context): user explicitly called this out ("There are two UI agents, run it by both!!! How did you miss this?"). Session 15: same mistake repeated because old agent output was treated as sufficient. Two UI agents exist for a reason: one checks visual polish/animation/spacing, the other checks flow/friction/cognitive load. They are not interchangeable. If the task touches UI and is T3+, both run. No exceptions.
95. **Framer Motion AnimatePresence directional animations need useRef, not useState.** When slideDirection is React state, both the exiting and entering components read the same (new) value because state updates are batched. Use a ref that's set synchronously before the state update that triggers the re-render. Combine with Framer Motion's `custom` prop + `variants` pattern for correct directional resolution.
96. **Hand-drawn SVG paths look terrible. Use Simple Icons.** Fetching official brand SVG paths from `https://raw.githubusercontent.com/simple-icons/simple-icons/master/icons/[name].svg` takes 30 seconds and looks professional. Hand-drawing SVG paths from memory produces unrecognizable shapes.
97. **Copy that implies exclusion creates doubt.** "SEO-friendly" on one path implies other paths aren't. "Works with every option above" implies it might not work without the qualifier. "You don't need to understand the code" is belittling. Write copy that's universally true and doesn't create accidental negative implications.
98. **Fixed modal height prevents jarring resizes between wizard steps.** Different steps have different content heights. Using `max-h` with auto height causes the modal to jump. Use fixed `h-[70vh]` with `flex flex-col`, `shrink-0` header, and `flex-1 overflow-y-auto` content.
99. **In the AI tools era, "non-technical" doesn't mean "can't use technical features."** It means they need their AI to help them. Showing React component benefits in plain English lets users ask their AI "should I use this?" Pro features should describe outcomes, not implementation details.
100. **Reading a skill file is NOT the same as applying it.** Session 15: read interface-design skill, listed it in "Skills loaded?", then wrote code without doing any of its mandatory pre-code steps (Intent statement, Domain Exploration, Mandate Checks). The skill was "loaded" into context but never executed. **Rule: when Step 1 field "Skills loaded?" lists a skill, Step 1 must also contain that skill's mandatory outputs.** For interface-design, that means Intent statements per change appear IN Step 1, not skipped. The check: if you remove the skill name from "Skills loaded?" and nothing else in Step 1 changes, you didn't apply the skill.
101. **Live competitor data beats knowledge cutoff.** Scraped pricing pages during this session revealed Testimonial.to's $21 Starter Plus tier is severely crippled (2 video total, no API, no Zapier, 1 space). This was not in training data. Always use Chrome/WebFetch for competitor claims.
102. **Porter's "stuck in the middle" is real for SaaS pricing.** $19/mo sat between budget ($9 to 10) and premium ($29) clusters. Customers comparison-shop and can't place you. Either go budget or go premium. Our visual quality justifies premium.
103. **Referral programs don't cause conversations at 0 to 50 users.** First-principles: referral incentives amplify existing word-of-mouth but don't create it. At 0 users, there's nobody to refer. Product quality drives organic conversations. Build referral infrastructure at Phase 5 (post-100 users), not before.
104. **Role-play buyer journeys with real data, not assumptions.** High-level "Persona X would choose us" is useless. Detailed role-plays with exact Google searches, comparison table construction, and price sensitivity at specific price points ($9/$19/$29/$39) reveal actual decision dynamics.
105. **todo.md can grow dangerously large.** At ~85KB, reading the full file wastes tokens. Use offset/limit. Consider splitting into separate strategy files if it grows further.
106. **Validate pain points against actual user complaints, not assumptions.** We assumed "widgets look out of place" was a customer pain point. Live research of G2 reviews, feedback boards, and forums found ZERO instances of users saying this. The real complaint is "limited customization options." Different problem, different solution. Always check: did we discover this pain point from real users, or did we assume it?
107. **"Native-looking" is a spectrum, not binary. The optimal position is NOT fully native.** Fully native = visitors think the company wrote it = trust lost. Fully foreign = banner blindness = gets skipped. Sweet spot = visual harmony (matching fonts/colors) + credibility signals (photos, names, verification badges, star ratings). Our credibility signals are MORE important than we initially thought.
108. **Stateful layouts in embed.js need `{html, mount}` pattern.** Pure HTML string rendering (used by grid, wall, list, single) can't add event listeners. For layouts with navigation/auto-rotate/swipe (editorial, carousel), return an object with `html` (string) and `mount` (function that takes rootContainer and wires up interactivity). Mount runs after shadow DOM assembly.
109. **Light/dark text detection must handle both hex AND rgb().** Only parsing `#rrggbb` breaks when users set `rgb(200,200,200)` as text color. Use a shared `parseColorBrightness()` helper that tries hex regex first, then `rgba?\(\s*(\d+)` regex. Returns -1 for unparseable (defaults to dark text, safe fallback).
110. **Dashboard preview colors must match embed.js colors exactly.** Using `theme.textColor + '6b'` (hex alpha append) produces different results than `rgba(0,0,0,0.42)` (which is what embed.js uses). Especially fails for non-hex colors. Both should use the same rgba computation.
111. **CSS animation classes must be wired up in JS, not just defined.** Defining `.ed-exit-up` and `.ed-enter-below` in CSS is useless if `goTo()` never adds those classes. Always trace CSS animation classes to their JS triggers. Review agents caught this.
112. **Touch targets: 44px minimum, no exceptions.** 36px arrow buttons felt fine on desktop but fail WCAG 2.5.8 on mobile. Always start at 44px for interactive elements.
113. **Gate at deployment, not discovery.** Locking premium features behind a paywall BEFORE the user experiences them kills conversion. Let users preview with their own data, gate at Save/export. This is how Canva, Figma, and every high-converting SaaS does it. Loss aversion + sunk cost + specificity > generic upgrade prompts.
114. **Fake macOS window chrome (traffic light dots) misleads users.** It makes a preview panel look like a standalone application window. The testimonials inside appear to BE the app rather than a preview of an embed. Use descriptive labels ("Preview: how it looks on your site") instead of decorative chrome.
115. **Competitor pricing page comparisons are NOT enough. You must use the product live.** Senja's pricing page says "3 forms, 1 project, 2 seats." What it doesn't say: 21 auto-import sources, 15 trigger integrations, AI search/sentiment, social video generation, 10-page form builder with conditional logic, gamification, CRM export. The feature gap is 10x larger than the pricing page suggests. Always create a competitor account and walk every flow.
116. **"We have more X" is a losing comparison strategy when the competitor has 10x more features overall.** Vouch wins on unlimited forms/projects at $29 vs Senja's caps. But Senja has 21 import sources, Zapier, AI, social videos, popups. Leading with "unlimited forms" while ignoring the 200-feature elephant in the room is intellectually dishonest. Comparison pages must lead with what we genuinely do better (output quality, simplicity), not with cherry-picked feature counts.
117. **The 80/20 rule applies to SaaS features. Most "templates" are cosmetic variations.** Senja's 22 widget templates map to only 7 distinct layout paradigms. 5 carousel templates are the same paradigm with different card styling. Vouch's 5 structural layouts already cover ~95% of real-world usage. Don't build 22 layouts. Build 7-9 great ones.
118. **Free tier generosity = growth engine, not revenue leak.** The "Powered by Vouch" badge on every free widget is organic marketing. Generous free tier (25 testimonials) means the widget looks impressive when visitors see the badge. Tally bootstrapped to $150K MRR this way. Move badge optimization from Phase 5 to Phase 1.
119. **Counter-position against complexity, not against the competitor directly.** "Senja has 200 features. You need 5. We built those 5 to be the best in the market." This turns the feature gap from a weakness into a strength. Customers who feel overwhelmed by Senja are our target.
120. **Notifications create dopamine loops that drive retention.** "New 5-star testimonial from Sarah Chen!" via Slack or email reinforces the tool is working. This is a high-impact, low-effort retention feature. Phase 2 priority.
121. **Let subagents read files themselves instead of pasting code into their prompts.** Subagents have their own context windows. Pasting code into agent prompts wastes BOTH main context and agent context. Let them use Read/Grep/Glob. Only paste small diffs (<50 lines). Always request concise summary output.
122. **CLAUDE.md should be under 100 lines.** Boris Cherny (Claude Code creator) keeps his at ~100. Ours was 640. Every line loads into every message. Move details to .claude/rules/ (auto-loaded, some path-specific). Went from 640 to 98 lines.
123. **Hooks are deterministic, CLAUDE.md is advisory.** Safety rules in CLAUDE.md can be forgotten mid-session. Hooks (PreToolUse, PostToolUse, Stop) execute every time, guaranteed. Put critical safety checks in hooks, not just instructions.
124. **PowerShell commands through bash lose $ signs.** On Windows, use .ps1 script files instead of inline PowerShell in bash hooks. The $ variables get stripped by bash interpolation.
125. **Set CLAUDE_CODE_SUBAGENT_MODEL env var for cost savings.** Anthropic's pattern: Opus orchestrates, Sonnet subagents execute. 40-50% cost reduction on focused tasks without quality loss.
126. **Multiple Upstash rate limiters need unique prefixes.** If two `Ratelimit` instances share the same prefix, they share Redis keys, meaning different endpoints (with different max/window) interfere with each other. Always pass a unique `prefix` per limiter (e.g., `vouch:rl:submit`, `vouch:rl:widget`).
